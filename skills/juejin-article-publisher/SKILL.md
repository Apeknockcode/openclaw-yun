## 📝 写作规范

### 核心原则：人味儿 > 技术深度

掘金有 AI 生成检测机制。纯 AI 输出的结构化内容（完整代码块、规整表格、模板化分段）容易被识别。**必须让文章读起来像一个人写的。**

### 文风要求

| 维度 | 要求 |
|------|------|
| 语气 | 技术专业但不刻板，像有经验的工程师在聊天 |
| 深度 | 中等偏深，3000-5000字 |
| 结构 | 层层递进，有实战有思考 |
| 代码 | 尽量不贴完整代码块，用一两行片段 + 文字描述代替。SQL/Python 等大段代码是 AI 检测的重灾区 |
| 例子 | 贴近真实开发场景，用亲历者的口吻 |
| 态度 | 可以吐槽、可以有观点，要逻辑自洽 |
| 标题 | 吸引技术人点击，不标题党 |

### 真人写作风格检查清单（通过/不通过的差异）

以下是从实战中总结的案例对比：

| 维度 | ❌ 被拒（AI感强） | ✅ 过审（人感强） |
|------|-----------------|-----------------|
| 开头 | 本文从实战角度拆解号卡分销场景下的佣金计算设计 | 做了两年佣金模块，踩了无数坑，今天掰开揉碎讲清楚 |
| 代码 | 完整 SQL 建表（4张表）、Python 函数 | 零完整代码块，用文字描述逻辑，最多一行片段 |
| 个人观点 | 几乎没有 | 大量：「说句实话」「我见过一个系统」「被现实狠狠教育了」 |
| 异常场景 | 列出来就完了 | 每个场景都配一个真实踩坑经历 | 
| 章节过渡 | 下面介绍... | 好了，说完了A，来聊聊B |
| 语气 | 专业、克制、客观 | 有褒有贬、有吐槽、有反思 |
| 格式 | 完美分段、规整表格、编号清晰 | 自然分段，偶尔用破折号和口语连接 |
| 结尾 | 总结关键结论 | 欢迎评论区聊聊你踩过什么坑 |

**黄金法则**：写完初稿后自检——如果觉得"这篇文章能被放在任何技术博客上" → 重写。如果觉得"这看起来像是我同事喝了两杯跟我吐槽的" → 对了。

## 📋 掘金审核规则（必读）

以下规则来自掘金官方，写作时必须逐条对照避免踩雷。

### 审核不通过类型

- **审核中**：内容发布后将进入审核状态
- **审核不通过**：系统会有消息提醒，需修改后重新提交
- **审核通过**：发布成功，可能获得推荐
- **内容被删除**：违反法律法规，直接删除

### 不会被推荐的文章类型

1. **非原创文章** — 百科式概念定义、个人备忘、书摘笔记，没有个人研究/洞察/实践体验。直接读官方文档无异，没有创造新的阅读价值
2. **标题过短或篇幅过短** — 标题只有一两个单词，或内容少于250字
3. **杂乱无序** — 排版混乱、结构不清晰、纯代码无文字描述
4. **配图不当** — 图裂、恶俗配图、品质过低
5. **⚠️ 推广类文章** — 招聘、广告、SEO、活动推广。**一经发现立即删除**
6. **⚠️ 引流类文章** — 加群二维码、个人微信、公众号二维码、**推广产品**。仅允许文字引导关注公众号
7. **标题党** — 夸大其词、题不对文、震惊党、两性吸睛
8. **面试类** — 机械罗列面试题、刷题打卡
9. **资讯类** — 搬运资讯、罗列链接、无个人观点
10. **非技术类** — 非技术类、无厘头内容

### 容易过审的文章特征

- 标题清晰概括、或问题导向（如"Redis为什么这么快？"）
- 排版有层级：开篇介绍 → 实现思路 → 文末总结
- 重点内容用颜色标注
- 有配图（示意图、思维导图、效果演示）
- 有自己的思考总结，而非概念罗列
- 文章类型属经验总结类、观点分享类、知识教学类

## 🚨 核心避坑指南（基于实战经验）

### 1. 去实名化规范（分析具体产品时）

当分析某款具体产品时，**不要在标题和开头直接出现产品名**，否则容易被判定为推广：

| 场景 | ❌ 错误写法 | ✅ 正确写法 |
|------|-----------|-----------|
| 标题 | 拆解分小号：一款垂直SaaS…… | 拆解一款号卡分销SaaS：…… |
| 正文首段 | 最近研究了一款产品叫「分小号」（fenxiaohao.com） | 最近研究了一款专注于这个赛道的SaaS产品 |
| 后续提及 | 分小号的核心功能…… | 这款产品的核心功能…… |
| 定价分析 | 分小号的定价策略…… | 定价策略非常清晰，三层结构…… |

**原则**：全文不出现产品名称、官网链接、品牌标识。用「这款产品」「该平台」「某号卡分销SaaS」等中性表述代替。

### 2. 严禁引流行为

**绝对不要写：**
- ❌ "建议你先去官网看看"
- ❌ "不妨去 xxx.com 注册一个免费版试试"
- ❌ "带着体感来读这篇文章，会有更多收获"
- ❌ 文末引导注册/体验/关注
- ❌ 放入任何外部平台的超链接

**允许：**
- ✅ 用文字描述产品功能（不出现品牌名时）
- ✅ 文末写"欢迎评论区讨论"
- ✅ 引用掘金站内文章链接

### 3. AI 内容检测规避（实战升级版）

这份规则来自实际两篇文章的对比经验——一篇过审、一篇被拒。

#### 被拒文章的失败特征（技术向文章，含完整SQL+Python代码）：
- ❌ 包含完整 `CREATE TABLE` 语句（4张表）
- ❌ 包含完整 Python 函数（带 docstring）
- ❌ 包含算法对比表
- ❌ 章节使用 `1.1`、`2.1` 这种标准编号
- ❌ 语气像技术文档/教科书
- ❌ 没有个人经历和真实案例
- ❌ 没有情感色彩（无吐槽、无感慨、无反思）

#### 过审文章的成功特征（产品分析向，无代码）：
- ✅ 大量个人观点：「我见过这样的系统」「说句实话」「踩了半年坑才想明白」
- ✅ 真实案例：「有一次因为一个佣金比例配置错了」→ 踩坑→修复→复盘
- ✅ 口语化语言：「别这么干」「被现实狠狠教育了」
- ✅ 有褒有贬：既说产品做得好，也说「这个功能比较标准，没有出彩的地方」
- ✅ 针对某个 topic 给出明确态度：「我的建议是」
- ✅ 开篇用个人经历引入，不是概念解释
- ✅ 零代码块，用一两行 SQL 片段或伪代码描述即可
- ✅ 章节标题像在聊天：「怎么存？」「实时算还是定时算？」

#### 关键结论：即使是技术文章，也要写成「一个人分享自己的实战经验」，而不是「一份技术教程文档」

**始终记住**：掘金的 AI 检测对以下模式特别敏感：
1. **完整代码块** — 能不贴就不贴，用文字描述代替
2. **规整表格** — 超过3列的对比表容易触发，用文字举例代替
3. **结构化章节编号** — 用自然小标题代替 1.1/2.1/3.1
4. **标准模板化结尾** — 用「欢迎评论区聊聊」代替「总结」

### 4. 标题编写规范

| 维度 | 要求 | 反例 |
|------|------|------|
| 长度 | ≤50字符 | — |
| 概括性 | 让人一眼知道讲什么 | Docker（太宽泛） |
| 去品牌化 | 不出现产品名 | 拆解分小号（有推广嫌疑） |
| 问题导向 | 可以提问方式 | Redis为什么这么快？✅ |
| 技术关键词 | 包含核心技术关键词 | — |
| 不标题党 | 不夸大、不震惊 | 震惊：这篇VUE的干货竟然说的这么全！❌ |

## 🎨 封面图规范

- **尺寸**：1200×675px（16:9）
- **风格**：技术感、简洁、有视觉冲击
- **内容**：文章标题大字 + 渐变背景 + 点缀元素

### 封面图生成方案（主方案）

使用 `image_generate` 生成封面图。

### 封面图生成方案（备用方案：Pillow Python 方案）

**⚠️ 注意：不要用 sharp SVG 方案。系统缺少 fontconfig 配置且无法安装，SVG 渲染中文字体为空白。改用的 Pillow 方案经过实战验证有效。**

使用 Python Pillow 生成封面：

```python
from PIL import Image, ImageDraw, ImageFont

W, H = 1200, 675
img = Image.new('RGBA', (W, H), (10, 22, 40, 255))
draw = ImageDraw.Draw(img)

# 渐变背景
for y in range(H):
    ratio = y / H
    r = int(10 + (26 - 10) * ratio)
    g = int(22 + (54 - 22) * ratio)
    b = int(40 + (96 - 40) * ratio)
    for x in range(W):
        draw.point((x, y), fill=(r, g, b, 255))

# 网格线
for x in range(0, W, 100):
    draw.line([(x, 0), (x, H)], fill=(30, 58, 95, 102), width=1)
for y in range(0, H, 100):
    draw.line([(0, y), (W, y)], fill=(30, 58, 95, 102), width=1)

# 装饰圆环
draw.ellipse([880, 0, 1120, 220], outline=(59, 130, 246, 38), width=1)
draw.ellipse([100, 450, 300, 650], outline=(6, 182, 212, 30), width=1)

# 连接点
dots = [(200,150), (350,200), (500,120), (650,250), (800,160), (950,220)]
connections = [(0,1), (1,2), (2,3), (3,4), (4,5)]
for i, j in connections:
    draw.line([dots[i], dots[j]], fill=(59, 130, 246, 76), width=1)
for dx, dy in dots:
    draw.ellipse([dx-4, dy-4, dx+4, dy+4], fill=(59, 130, 246, 76))

# 底部/左侧强调线
draw.rectangle([(0, H-4), (W, H)], fill=(59, 130, 246, 204))
draw.rectangle([(0, 0), (6, H)], fill=(59, 130, 246, 153))

# 字体（使用 Noto Sans CJK Bold）
font_title = ImageFont.truetype("/usr/share/fonts/google-noto-cjk/NotoSansCJK-Bold.ttc", 64, index=0)
font_sub = ImageFont.truetype("/usr/share/fonts/google-noto-cjk/NotoSansCJK-Regular.ttc", 28, index=0)
font_tag = ImageFont.truetype("/usr/share/fonts/google-noto-cjk/NotoSansCJK-Regular.ttc", 16, index=0)

# 标题居中
def center_text(text, font, y):
    bbox = draw.textbbox((0, 0), text, font=font)
    tw = bbox[2] - bbox[0]
    return (W - tw) // 2, y

tx, ty = center_text(TITLE, font_title, 220)
draw.text((tx, ty), TITLE, fill=(255,255,255), font=font_title)

tx, ty = center_text(SUBTITLE, font_sub, 310)
draw.text((tx, ty), SUBTITLE, fill=(148,163,184), font=font_sub)

# 标签徽章
tag = TAG_TEXT
bbox = draw.textbbox((0, 0), tag, font=font_tag)
tag_w = (bbox[2] - bbox[0]) + 60
tag_h = (bbox[3] - bbox[1]) + 20
tag_x = (W - tag_w) // 2
tag_y = 380
draw.rounded_rectangle([(tag_x, tag_y), (tag_x + tag_w, tag_y + tag_h)], radius=18,
                       fill=(59, 130, 246, 51), outline=(59, 130, 246, 102), width=1)
draw.text((tag_x + 30, tag_y + 10), tag, fill=(147, 197, 253), font=font_tag)

img.save('/root/.openclaw/workspace/juejin_cover_YYYYMMDD.png')
```

使用步骤：
1. 将 `TITLE`、`SUBTITLE`、`TAG_TEXT` 替换为对应文字
2. 执行 Python 脚本（需要 Pillow 库，已预装）
3. 输出文件为 `juejin_cover_YYYYMMDD.png`

## 🔄 创作流程

### Step 1: 判断上下文（不废话）
- 检查当前会话是否已有讨论的主题 → 直接用
- 检查 workspace 是否有未完成的 juejin_draft → 检查状态/询问是否继续
- 如果没有主题 → 问一次，不多次重复

### Step 2: 判断文章类型

**类型A - 纯技术文章/实战经验**（我踩过的坑系列）：
- 优先用「个人踩坑经历」的风格，不要写成教程
- 尽量不贴完整代码块，用文字描述 + 一两行片段
- 每个章节必须有一个真实踩坑故事
- 有个人态度和吐槽

**类型B - 产品分析/行业观察**：
- 必须去实名化，不出现具体产品名
- 有褒有贬，不纯赞美
- 增加个人观点和分析深度
- 不放入外部链接

### Step 3: 写作 + 封面 + 元数据（同步输出）

写作完成后，**必须一次性输出以下内容**：
1. 文章完整 Markdown（直接展示在回复中）
2. 封面图（用 `MEDIA:` 展示）
3. 元数据（标题/分类/标签）
4. 发布步骤指引

**严禁**让用户追问才补全内容。

## 🔧 审核未通过处理流程

### 步骤 1: 确认被拒类型
先问用户审核消息具体提示了什么。

### 步骤 2: 按优先级排查

**高优先级 - AI 检测嫌疑（最常见）：**
- 检查是否包含完整代码块（SQL/Python/Java 等）→ 删除，改为文字描述
- 检查是否包含规整对比表 → 拆成文字举例
- 检查是否缺乏个人观点 → 每章节加一段「说句实话」
- 检查是否结构太模板化 → 调整分段，加入口语化过渡
- 检查是否缺乏真实案例 → 加至少 2-3 个"我见过"/"有一次"的真实故事
- **直接参考用户历史过审文章的风格进行重写**

**中优先级 - 推广/引流嫌疑：**
- 检查标题是否包含产品名 → 去实名化
- 检查正文是否有外部链接 → 删除
- 检查是否有引导注册/体验 → 删除全部CTA

**低优先级 - 其他：**
- 字数是否达标（≥250字）
- 排版是否清晰
- 配图是否有效

### 步骤 3: 修改后直接输出完整版
修正后直接重新呈现完整 Markdown + 封面，不要只给差异。
